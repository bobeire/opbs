User-state migration · new in 0.6.88

New PC.
Same you.

When a machine is replaced or Windows is reinstalled, OPBS moves what you actually care about — Documents, Desktop, browser profiles, chat histories, game saves, per-user settings — from your old disk image (or the old drive itself) onto the running new install. Dry-run by default, refuses up front, verifies after. And it hands you a winget manifest so your apps come back too.

What actually moves

Three tiers, each with its own mechanism — and its own honest boundary.

Tier What How Status
1 · Profile data Documents, Desktop, Downloads, Pictures…, %APPDATA% / %LOCALAPPDATA%, known app data stores File copy with per-file journal and MD5 verification ✓ shipped
2 · Per-user settings Curated per-user registry keys — browsers, terminals, app preferences living in NTUSER.DAT Key-level offline hive transplant: load, copy key by key, count-verify, unload ✓ shipped
3 · Your programs Installed-app inventory from the source's uninstall keys winget-import.json plus a human-readable reinstall list ✓ shipped
OPBS never copies installed program binaries — on purpose. Licensing, COM registrations, services and drivers make that a trap even commercial tools fail at. The honest 2026 answer is winget import on the new machine, and OPBS builds that manifest for you from what it finds on the old one.
Identity is handled, not assumed. The new account's SID never matches the old one — files are copied as you (elevated), then the owner of the copied tree is rewritten to the target profile's SID so inherited rights just work. Saved browser passwords sit behind DPAPI, which is machine-bound: copied profiles may need one re-login, and the report says so.

Start from what you already have

Every source funnels into the same thing OPBS already reads better than anyone: an NTFS volume and its user profiles.

🖼 An old machine's image

Point at an .opbs, Macrium .mrimg or .mrimgx backup and pull the profiles straight out of it — no original hardware needed. OPBS reads the Macrium formats natively ↗, chains included.

💽 The old drive, plugged in

Pull the disk, plug it in — the classic two-machine swap. OPBS reads the volume directly, finds the profiles and inventories what's on them.

💾 Restore into a VHD first

The flagship path: restore the old machine into a virtual disk on the new PC, attach it, and migrate the profiles onto the live OS. No bare-metal restore on the target, no second machine needed.

🔗 Read-only mount

Mount a partition from any image as a real drive letter via WinFsp and migrate from there — reads are served on demand, the image is never written.

Source images are read-only, always. Inventory and plan don't write a single byte. Everything happens against the live target, and only after you accept a plan.

Dry-run first — always

The same trust contract as OPBS restores, applied end to end.

  1. Inventory (read-only)

    Profiles and SIDs on the source, app scan through the knowledge base, known store detection (mail, browsers, chat, saves), and a free-space check on the target.

  2. Plan (read-only)

    Every file move with sizes, every registry key, every refusal with a reason — and a plan hash. migrate plan exits 1 when refusals exist, so scripts can't sleepwalk past them.

  3. Execute

    --execute requires handing back the hash the plan printed. Every file is journalled, so a crash mid-profile leaves a journal you can --resume. Existing target files abort that profile unless you pass --merge.

  4. Verify & report

    A full MD5 pass over what was copied, then report.json + winget-import.json under .opbs-migrate/ — migrated, skipped, refused and needs-reinstall, with paths.

Refused up front, never halfway: a locked BitLocker source, missing image chain members, not enough free space on the target, a target profile that doesn't exist yet — OPBS does not create Windows accounts, so create the account (and log in once) first — and apps it can't safely classify ask for an explicit --include.

The Migrate wizard

A GUI over the exact same CLI verbs — five steps, nothing off-script.

🗂 Source & profile

Pick a live system drive or an image (with partition and passphrase), then choose the profile to migrate. Listing is a cheap in-process scan of Users\ — no store walk.

🎯 Target

Point at the existing profile folder on the new install. OPBS verifies it really is a directory before you can continue — no discovering a typo at execute time.

📋 Plan review

Totals, plan hash, registry keys, winget reinstall hints and every refusal in the open. The execute button stays disabled while any refusal exists.

⚙️ Options

Registry transplant (only offered when elevated), owner/SID rewrite (on by default when elevated), and merge / resume / no-verify switches for the special cases.

▶️ Run & report

Progress streams from the copy journal as files land, and ends in the full report — summary, registry outcomes, owner status, and artifacts you can open with one click.

🧒 Never blocks the app

The wizard spawns the CLI in a child process; JSON arrives via files and passphrases via short-lived temp files — never on the command line, never on the main loop.

And you can rehearse it. Settings → Scheduled Migration Drills runs a strictly read-only migrate plan against the newest image on a cron you pick, records the result next to the image in opbs-migrate-drill-history.json, and only raises an alert after several consecutive failures. Headless CLI

Every verb is scriptable — read-only JSON out, execute gated on a plan hash. 

:: read-only inventory of an image partition
OPBS.exe --cli migrate inventory "D:\Images\old-pc.mrimg" --partition 1

:: dry-run plan — prints the plan hash, exits 1 if anything is refused
OPBS.exe --cli migrate plan "D:\Images\old-pc.mrimg" --partition 1 --profile all

:: execute — hand the plan's hash back; add --registry in an elevated shell
OPBS.exe --cli migrate run "D:\Images\old-pc.mrimg" --partition 1 --profile alice --target C:\Users\alice --execute --plan-hash <hash> --registry

:: the same thing from the live machine you are sitting at
OPBS.exe --cli migrate inventory --live
  • --json / --json-out FILE — machine-readable plan, run and inventory output for automation.
  • --apps-db my.json — merge your own app entries over the 43-app seed (validated on load).
  • --passphrase — encrypted source images; the GUI hands it over as a short-lived file instead of argv.
  • --folder / --target / --profile — scope a single folder or profile instead of everything.

A knowledge base you can read

Where per-app data lives, which registry keys are safe to move, and what to reinstall — as a plain JSON file in the repo, not a black box. 

{
  "id": "google-chrome",
  "name": "Google Chrome",
  "data": ["%LOCALAPPDATA%/Google/Chrome/User Data"],
  "registry": ["HKCU/Software/Google/Chrome"],
  "winget": "Google.Chrome",
  "class": "data+settings"
}
  • 43 seed apps across browsers, mail, chat, dev tools, media, utilities and game launchers — every winget id verified against winget-pkgs.
  • Classes: data, data+settings, reinstall-only (AV, Office, COM-heavy — data paths ignored), ignore.
  • Validated on load — HKCU-only registry keys (HKLM is never written), known %TOKENS%, no drive-absolute paths, Publisher.Package winget shape.
  • Contribute an entry — copy a seed entry, verify the winget id, test it against a real profile with --apps-db, and open a PR. Entries land with the next release.

Honest limits

What OPBS won't do — because a migration tool that oversells itself is worse than one that doesn't.

  • Program binaries stay put. You get a winget manifest and a human-readable list instead — by design, not a gap.
  • No HKLM, no OS migration. The target runs its own Windows; OPBS moves user state into it, key-level only, from curated per-user keys.
  • Driver-level software is reinstall-only: antivirus, virtual-disk filters, niche hardware suites.
  • Workgroup machines in v1. Domain/GPO-managed state re-applies itself from policy anyway.
  • x64 → x64 in v1, Windows-only, and v0.6.x: real tests, real verification, still young in the field.
  • EFS and BitLocker: encrypted files copy decrypted and are flagged in the report; locked BitLocker sources are refused until you unlock them.
  • If your old machine is domain-joined, or you need certified compliance and an enterprise support contract, Microsoft's USMT or a paid vendor is the right call.
